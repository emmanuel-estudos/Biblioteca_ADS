# Atividade 02

Guia Prático: Configuração de Redes Overlay (VXLAN e GRE) com Open vSwitch.

Este guia tutorial apresenta o passo a passo para a configuração de uma rede de sobreposição (*Overlay*) utilizando os protocolos VXLAN e GRE sobre uma infraestrutura base (*Underlay*), simulada através de três Máquinas Virtuais (VMs). Este experimento é fundamental no contexto de Segurança de Dados para compreender o isolamento lógico de tráfego e o tunelamento em redes definidas por software (SDN).

---

## Inicialização e Preparação do Ambiente (VM3)

O primeiro passo consiste em inicializar as três máquinas virtuais. Na VM3, que atuará como o nó central da infraestrutura de transporte (*Underlay*), precisamos elevar os privilégios para super-usuário e iniciar a interface gráfica para gerenciar os terminais de forma organizada.

  <Abas>

    <Aba active>VM3</Aba>
  </Abas>
  <Code>
    <Comentario>Elevando privilégios para root</Comentario>

Com a interface gráfica iniciada na VM3, abra o `LXTerminal` e crie três abas utilizando o atalho `Ctrl + Shift + T`. Nomeie cada uma das abas como VM1, VM2 e VM3 para facilitar a identificação do fluxo de trabalho.

## Configuração do Roteamento Underlay (VM1 e VM2)

Para que as redes isoladas consigam estabelecer túneis, a infraestrutura base precisa conseguir rotear os pacotes entre os nós. Na aba correspondente à VM1, faremos um acesso seguro via SSH para o nó correspondente na sub-rede `192.168.1.10`, seguido da elevação de privilégios e a adição de uma rota estática para a rede interna da VM2 através do gateway da VM3.

<Terminal>
  <Abas>
    <Aba active>VM1</Aba>
    <Aba>VM2</Aba>
    <Aba>VM3</Aba>
  </Abas>
  <Code>
    <Comentario>Acessando a VM1 via SSH na rede local</Comentario>
    <Linha texto="mininet@mininet-vm:~$">ssh mininet@192.168.1.10</Linha>
    <Linha texto="mininet@192.168.1.10's password:">mininet</Linha>
    <Comentario>Virando super-usuário para aplicar configurações de rede</Comentario>
    <Linha texto="mininet@vm1:~$">sudo su</Linha>
    <Comentario>Adicionando rota para a rede da VM2 apontando para o gateway da VM3</Comentario>
    <Linha texto="root@vm1:/home/mininet#">route add -net 192.168.2.0 netmask 255.255.255.0 gw 192.168.1.1</Linha>
  </Code>
</Terminal>

De forma simétrica, faremos o mesmo procedimento na aba da VM2. Conectaremos via SSH no IP `192.168.2.20`, assumiremos o perfil de super-usuário e adicionaremos a rota de retorno para a sub-rede da VM1 (`192.168.1.0/24`) utilizando o respectivo gateway da infraestrutura de transporte.

Isso ocorre porque o nó central (VM3) ainda não está autorizado pelo sistema operacional a atuar como um roteador de pacotes transitórios, resultando em perda total de dados. No entanto, o ping para o gateway local da infraestrutura deve responder perfeitamente.

## Ativação do Encaminhamento IP (IP Forwarding) na VM3

Para corrigir a falha de comunicação identificada no teste anterior, devemos ir até a aba da VM3 (Underlay). Primeiramente, inspecionamos o estado do parâmetro de kernel para repasse de pacotes IPv4 que estará desativado (retornando `0`). Em seguida, escrevemos o valor `1` diretamente no sistema de arquivos virtual `/proc` para instruir o Linux a rotear pacotes entre as interfaces e validamos se a alteração foi aplicada com sucesso.

<Terminal>
  <Abas>
    <Aba>VM1</Aba>
    <Aba>VM2</Aba>
    <Aba active>VM3</Aba>
  </Abas>
  <Code>
    <Comentario>Verificando estado atual do encaminhamento IP</Comentario>
    <Linha texto="root@vm3:/home/usuario#">cat /proc/sys/net/ipv4/ip_forward</Linha>
    <Resultado>0</Resultado>
    <Comentario>Ativando o IP Forwarding dinamicamente</Comentario>
    <Linha texto="root@vm3:/home/usuario#">echo 1 > /proc/sys/net/ipv4/ip_forward</Linha>
    <Comentario>Confirmando que o parâmetro agora está ativo (1)</Comentario>
    <Linha texto="root@vm3:/home/usuario#">cat /proc/sys/net/ipv4/ip_forward</Linha>
    <Resultado>1</Resultado>
  </Code>
</Terminal>

Com o encaminhamento de pacotes ativado no núcleo da rede de transporte, podemos retornar às máquinas das pontas para validar o tráfego de interconexão. Executando o comando de ping a partir da VM1 em direção à VM2 (e vice-versa), os pacotes agora serão devidamente encaminhados através da VM3 com sucesso na transmissão.

<Terminal>
  <Abas>
    <Aba active>VM1</Aba>
    <Aba>VM2</Aba>
    <Aba>VM3</Aba>
  </Abas>
  <Code>
    <Comentario>Testando novamente o ping da VM1 para a VM2 após ativação na VM3</Comentario>
    <Linha texto="root@vm1:/home/mininet#">ping -c 4 192.168.2.20</Linha>
    <Resultado>4 packets transmitted, 4 received, 0% packet loss</Resultado>
  </Code>
</Terminal>

## Inicialização dos Cenários SDN e Criação do Túnel VXLAN

Agora que temos a conectividade básica estabelecida na rede física (Underlay), iniciaremos a criação da rede virtual de sobreposição (*Overlay*). Na VM1, verificamos os arquivos locais usando o comando `ls` e inspecionamos as regras iniciais contidas no arquivo `flows1.txt`. Na VM2, listamos os arquivos e abrimos brevemente o script Python gerador da topologia para revisão antes de executá-lo.

<Terminal>
  <Abas>
    <Aba>VM1</Aba>
    <Aba active>VM2</Aba>
    <Aba>VM3</Aba>
  </Abas>
  <Code>
    <Comentario>Listando diretório e abrindo o script de topologia no editor de texto pico</Comentario>
    <Linha texto="root@vm2:/home/mininet#">ls</Linha>
    <Linha texto="root@vm2:/home/mininet#">pico VXLANexample2.py</Linha>
    <Comentario>Use Ctrl + X para sair do editor de texto</Comentario>
  </Code>
</Terminal>

Limpamos a tela do terminal da VM1 utilizando o atalho `Ctrl + L` para organizar o ambiente. Em seguida, iniciamos os scripts Python de simulação do Mininet em ambos os nós (`./VXLANexample1.py` na VM1 e `./VXLANexample2.py` na VM2) para instanciar os switches virtuais Open vSwitch locais que gerenciarão o tráfego encapsulado.

<Terminal>
  <Abas>
    <Aba active>VM1</Aba>
    <Aba>VM2</Aba>
    <Aba>VM3</Aba>
  </Abas>
  <Code>

</Terminal>

Com os switches em execução, aplicamos as tabelas de fluxos OpenFlow a partir do arquivo texto e criamos a interface de túnel virtual utilizando o protocolo **VXLAN** no switch `s1` da VM1, definindo o IP remoto correspondente à VM2 e especificando mapeamento via chaves dinâmicas.

<Terminal>
  <Abas>
    <Aba active>VM1</Aba>
    <Aba>VM2</Aba>
    <Aba>VM3</Aba>
  </Abas>
  <Code>
    <Comentario>Injetando os fluxos OpenFlow no switch s1</Comentario>
    <Linha texto="root@vm1:/home/mininet#">sh ovs-ofctl add-flows s1 flows1.txt</Linha>
    <Comentario>Criando o endpoint do túnel VXLAN apontando para a VM2</Comentario>
    <Linha texto="root@vm1:/home/mininet#">sh ovs-vsctl add-port s1 vtep -- set interface vtep type=vxlan options:remote_ip=192.168.2.20 option:key=flow ofport_request=10</Linha>
  </Code>
</Terminal>

Para fechar o enlace do túnel, executamos os comandos correspondentes no switch `s2` da VM2, associando seu respectivo arquivo de fluxos e apontando o endereço remoto do túnel de volta para o IP da VM1 (`192.168.1.10`).

<Terminal>

  </Abas>

O tráfego trafega encapsulado em pacotes UDP de forma transparente pela rede física. Lembre-se de registrar um print de comprovação desta etapa.

## Comparativo de Infraestrutura Overlay com Túnel GRE

Após testar o VXLAN, encerramos a aplicação e as simulações nas instâncias virtuais das pontas para realizar uma análise comparativa utilizando outro protocolo clássico de tunelamento: o **GRE (Generic Routing Encapsulation)**. Na VM1, limpamos as configurações anteriores e reinjetamos as regras especificando o tipo do link como `gre`.

<Terminal>
  <Abas>
    <Aba active>VM1</Aba>
    <Aba>VM2</Aba>
    <Aba>VM3</Aba>
  </Abas>
  <Code>
    <Comentario>Recriando os fluxos e instanciando o túnel utilizando o protocolo GRE na VM1</Comentario>
    <Linha texto="root@vm1:/home/mininet#">sh ovs-ofctl add-flows s1 flows1.txt</Linha>
    <Linha texto="root@vm1:/home/mininet#">sh ovs-vsctl add-port s1 vtep -- set interface vtep type=gre options:remote_ip=192.168.2.20 option:key=flow ofport_request=10</Linha>
  </Code>
</Terminal>

Finalizamos a configuração em espelho na VM2, limpando os resquícios do ambiente anterior, carregando a tabela de fluxos `flows2.txt` no switch virtual `s2` e alterando a interface VTEP local para operar também no modo `gre`.

<Terminal>
  <Abas>
    <Aba>VM1</Aba>
    <Aba active>VM2</Aba>
    <Aba>VM3</Aba>
  </Abas>
  <Code>
    <Comentario>Configurando o endpoint do túnel do tipo GRE na VM2 direcionado para a VM1</Comentario>
    <Linha texto="root@vm2:/home/mininet#">sh ovs-ofctl add-flows s2 flows2.txt</Linha>
    <Linha texto="root@vm2:/home/mininet#">sh ovs-vsctl add-port s2 vtep -- set interface vtep type=gre option:remote_ip=192.168.1.10 option:key=flow ofport_request=10</Linha>
  </Code>
</Terminal>

Realizamos o teste final de conectividade utilizando o comando de ping a partir do host `blue2`. Note que o tráfego na sub-rede isolada `10.0.0.0` funcionará de forma muito semelhante ao cenário anterior, contudo, a diferença reside na arquitetura de segurança e cabeçalhos de pacotes: o GRE opera diretamente sobre a camada IP (protocolo IP 47), enquanto o VXLAN introduz encapsulamento baseado em Camada 2 sobre UDP.
